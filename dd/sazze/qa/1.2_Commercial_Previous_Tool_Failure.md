# Previous Tool/Method and Failure Points

## 질문
For your pilots, what tool or method did they use immediately before Sela, and what specifically failed?

## 답변

파일럿 고객들이 기존에 사용하던 방식과 실패 지점:

기존 방식:
- 자체 스크래핑 스크립트 (Puppeteer, Playwright 등)
- 중앙화 프록시 서비스 (Bright Data, Smartproxy 등)
- 클라우드 브라우저 서비스 (Browserbase, Tavily 등)

주요 실패 지점:
- 인증 실패: 로그인이 필요한 플랫폼(LinkedIn, X 등) 데이터 접근 불가
- IP 차단: 서버/데이터센터 IP 기반으로 대량 요청 시 차단율 증가
- 스케일링 한계: 중앙화 인프라 증설 비용 및 시간 부담
- 유지보수 부담: 플랫폼 구조 변경 시 스크립트 수정 필요

Sela 전환 이유:
- Residential IP + 인증된 세션으로 높은 성공률
- 분산 노드로 자연스러운 스케일링
- API 호출만으로 웹 액션 실행 (스크립트 유지보수 불필요)

---

## Answer (English)

Previous methods and failure points used by pilot customers:

Previous Methods:
- Self-built scraping scripts (Puppeteer, Playwright, etc.)
- Centralized proxy services (Bright Data, Smartproxy, etc.)
- Cloud browser services (Browserbase, Tavily, etc.)

Key Failure Points:
- Authentication failures: Unable to access data on platforms requiring login (LinkedIn, X, etc.)
- IP blocking: Increased block rates for bulk requests from server/datacenter IPs
- Scaling limitations: Cost and time burden for centralized infrastructure expansion
- Maintenance burden: Script modifications required when platform structures change

Reasons for Switching to Sela:
- High success rates with Residential IP + authenticated sessions
- Natural scaling through distributed nodes
- Web action execution with just API calls (no script maintenance required)
